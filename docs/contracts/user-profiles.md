# 설치본과 사용자 프로필

일반 사용에 HM 소스 레포·Git·GitHub 로그인이 필요하지 않다. 공통 기본 정의는 main 번들에 포함하고, Windows Node 보호 스크립트는 기존 asar unpack 경로를 사용한다. 소스 경로는 개발자 마켓플레이스와 기존 레포 가져오기용 선택 사항이다.

## 로컬 저장과 편집

- 선택: `settings.json.setupProfileId`. `core/dev/full`은 별도의 설치 범위다.
- 정의: `~/.harness-manager/profiles/<id>/definition/{manifest,home}`.
- 개인 설정: `<id>/local/`. `private-terms.json`은 없으면 빈 목록으로 초기화한다. 가져오기 화면에서 저장·수정할 수 있고 손상된 목록도 원본 백업 후 복구한다.
- 기본 정의는 읽기 전용이다. 개인 사본은 앱 업데이트로 덮어쓰지 않는다. 기존 `legacy` 선택은 원본을 보존해 개인 사본으로 이전한다.
- 보관은 등록 정보만 바꾼다. 연결한 외부 폴더도 지우지 않는다.
- 편집은 `profiles:editor` → `profiles:preview` → `profiles:apply`. main이 문서를 검증하고 미리보기 토큰과 원본 지문을 다시 확인한다. 실행 명령을 renderer에서 직접 받지 않는다.
- 저장·받기는 실제 PC 설정이나 패키지를 변경하지 않는다. 실제 반영은 기존 install의 계획·미리보기·실행·검증 절차를 거친다.

## 이동 형식

`.hmprofile.json`은 `{ format: "harness-manager-profile", version: 1, name, files, personal }` JSON이다. `files`와 `personal`은 고정 allowlist의 상대 파일명 → UTF-8 텍스트 맵이다. 파일별 2 MiB, 가져오기 전체 16 MiB 상한을 적용한다. 파일 경로와 상위 폴더의 symlink를 따라가지 않는다.

개인 설정 이동 선택은 로컬 `portability.json`에 기억한다. 선택한 개인 지침·이메일 등은 포함할 수 있으나 인증 정보와 PC 고유 절대경로는 제외한다. 정의 파일에 이런 값이 있으면 내보내기를 막고 수정하도록 안내한다. 비공개 낱말 검사는 공개 소스 게시와 capture의 개인 값 분리에 계속 사용한다. 인증 검사와 별개다.

가져오기는 새 ID로 등록한다. 새 형식·임의 파일·손상된 manifest를 거부한다. 계정 로그인 파일, 환경변수 실제 비밀값, 원본 설치 로그는 형식에 포함하지 않는다.

## GitHub 동기화

Git과 GitHub CLI를 선택 기능으로 사용한다. 새 비공개 저장소를 만들거나 기존 HM 프로필 저장소를 연결하며, 브라우저 로그인과 인증 저장은 GitHub CLI가 담당한다. 앱 자체 OAuth 서버는 없다.

원격에는 `profile.hmprofile.json` 하나를 관리한다. 로컬 `<id>/github.json`은 원격 이름·기준 커밋·마지막 동기화 내용을 보관한다. 전용 작업 사본은 `~/.harness-manager/profile-sync/` 아래에 만든다. 사용자 Git 작업 폴더를 reset하거나 강제로 push하지 않는다.

- 앱 시작·수동 확인에서 변경을 알린다. 보내기·받기는 미리보기 후 실행한다.
- 보내기는 원격 기준이 같을 때만 수행한다. 비공개 여부를 확인하고 파일 하나만 커밋·push한다.
- 받기는 기준·로컬·원격의 파일별 차이를 비교한다. 충돌은 로컬 또는 원격을 명시 선택한다. 첫 받기는 원격을 기준으로 하며 기존 로컬 파일은 백업한다.
- 적용 직전 원격 커밋·연결·로컬 지문을 다시 검사한다. 원격 공개 전환·인증 실패·취소 시 실제 설치를 수행하지 않는다.
- 설치·AI 복구와 편집·동기화 적용은 같은 실행 관문으로 서로 배제한다.

CLI도 같은 서비스를 사용한다. `hm profiles export/import`와 `sync`는 기본 미리보기이며 `--yes`가 있어야 적용한다. 충돌은 `--prefer local|remote`로 명시한다.

## AI 기여

`repair:run`의 기여 방식은 `none`이 기본이다. 요청별 별도 동의에 따라 `pr` 또는 `direct`를 전달한다. `none`은 소스 준비·게시를 수행하지 않는다.

`pr`은 공식 upstream의 독립 사본에서 수정하고 테스트·타입 검사·빌드와 공개 노출 검사를 통과한 뒤 사용자 fork의 작업 브랜치에 push하고 `dev` 대상 PR을 만든다. `direct`는 명시적 관리자 설정과 GitHub 쓰기 권한이 필요하다. 사용자 개발 레포 작업 트리는 건드리지 않는다. 자동 태그·배포·병합은 없다.

PC 복구와 게시 결과는 독립적으로 표시한다. 게시 실패는 사본을 보존하며 현재 앱 세션에서 `repair:retry-source`로 다시 검증·게시한다. 재시작 후에는 보존된 작업 사본을 수동으로 이어갈 수 있다.

## 검증

Vitest는 임시 HM 홈을 사용한다. 저장·이동, 없는 비공개 낱말 초기화, legacy 이전, 경로·형식 검증, 동기화 충돌·취소·공개 전환, 기여 미동의·fork PR·관리자 권한·게시 재시도를 검증한다. Git 테스트는 임시 bare 저장소와 모의 GitHub 응답을 사용한다. 설치본 검증도 별도 홈에서 수행하며 실제 패키지 설치·로그인·원격 저장소 생성은 실행하지 않는다.
